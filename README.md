# ELVARN V1

A small decoder-only Transformer language model written in PyTorch, with a
fixed byte-level BPE tokenizer, a document-level train/validation split, and a
local browser chat UI that shows the text generated by your own checkpoint.

ELVARN is a small model trained on a limited corpus. Its replies are generated
text and can be wrong, repetitive or incomplete. Nothing in the training data
is "verified" just because it is in the corpus; the domain blocks are marked
`Unverified - pending source check`.

## What this project is

ELVARN is a small language model (17M parameters, 512-token context) wrapped in a system that gives it **grounded, cited answers about Tamil Nadu corruption cases (1947-2026)** and **refuses instead of inventing** when it has no record.

**Live demo:** https://elvarn.onrender.com (free hosting: the first request after a quiet period can take up to a minute while the services wake up).

The model alone cannot recall facts, so it never answers from memory. Each question is routed:

```
question
  |-- corruption question --> GraphRAG over stored records
  |       Neo4j knowledge graph (facts, ontology)  ||  Chroma vector search (all passages)
  |       -> merge and rank -> the model writes the answer from the cited records
  |       -> no match? "Not found in my data."  (never invented)
  |-- general / time-sensitive question --> live web search (SearXNG) -> model writes from the results
  `-- chat / creative --> the model alone (and the UI says so)
Redis keeps per-session memory (follow-ups like "what was the outcome?") and a retrieval cache.
```

Every answer carries an **"Answered from"** label (stored records / live web search / the model alone / nothing) and clickable **source cards**.

### Parts

| Part | What it does |
|---|---|
| `backend/model/`, `backend/training/` | The 17M decoder-only Transformer, byte-level BPE tokenizer, resumable training |
| `backend/knowledge/` | Ontology (`ontology.ttl`), Neo4j store, Chroma store, GraphRAG pipeline, snapshot export/import |
| `knowledge_service/` | One free self-contained Docker service (read-only snapshot of the knowledge base + embedded Chroma + local Redis), token-protected |
| `backend/pipeline/`, `dags/` | Daily collection (DVAC, CBI, Supreme Court, Madras High Court) through Kafka and Spark, scheduled by Airflow, de-duplicated, gated retraining |
| `backend/search/`, `search_service/` | Live web search through a self-hosted SearXNG, with a router that decides when to search |
| `backend/api/`, `frontend/` | FastAPI server and the chat UI (formatted answers, source drawer, PDF / Word / TXT export, rename and pin sessions) |
| `scripts/deploy_render.py` | Creates the knowledge service on Render through its API and wires the site to it |

Hosted snapshot (2026-10-14): 7,024 graph nodes, 5,872 relationships, 9,781 searchable passages. 874 automated tests.

### Honest limits

- The 17M model writes poorly: even with the right records, its wording can be garbled. The records and citations are the trustworthy part, so check the source cards.
- No facts are human-approved yet (about 1,400 proposed facts wait for review).
- Exact rare names and numbers can be missed by retrieval, and live web search quality varies.

## How the pieces fit

1. `corpus.py` turns each raw file into documents (one per `<TAG>` block, or
   paragraph groups for plain text), removes duplicates, assigns about 5% of
   documents to validation, and removes any training document that is a
   near-duplicate of a validation document. Splitting is by document, before
   any sequences are made, so validation text is never seen in training.
2. `train_bpe.py` trains the tokenizer on the **training** documents only.
   Special tokens: `<PAD>`=0, `<UNK>`=1, `<BOS>`=2, `<EOS>`=3, plus the four
   category tags. The vocabulary is fixed after training.
3. `build_dataset.py` writes each split as `<BOS> text <EOS>` token streams.
4. `train_batch.py` samples random windows of 128 tokens, predicts the next
   token at every position, and ignores `<PAD>` in the loss. It evaluates on the
   validation split every 250 steps. `final.pt` holds the best-validation
   weights and `latest.json` points at it. The server only loads a run that
   is marked `completed`, and refuses a checkpoint whose tokenizer hash
   differs from the saved tokenizer.
5. The server builds a prompt in the same format as the training data (for
   example `<CASUAL_CONVERSATION>\nUser: hii\nAssistant:`), generates token by
   token with the loaded model, and returns the text. The UI shows it
   unchanged. Generation stops at `<EOS>`, at the start of a new
   `User:`/`Question:`/block, or at the token limit. Use **Show raw model
   output** in the lab panel to see everything the model produced.

## Model

Sizes are presets chosen with `--size` (`tiny`, `7m`, `1b`). Training refuses a size that will not fit in RAM (the `1b` preset is about 1.0 billion parameters and needs about 16 GB just for training state, so it needs a bigger machine). Each training run keeps its own copy of the tokenizer next to its checkpoint, and the server loads that copy.

Default `tiny` model: token + learned position embeddings, 2 decoder blocks (4 attention heads,
post-norm, GELU MLP), final LayerNorm, output head tied to the token embedding.
Embedding 128, hidden 256, context 128 tokens, about 0.8M parameters.
Dropout 0.1. Everything runs on CPU.

Choices worth knowing:

* **Vocabulary.** `train_bpe.py` defaults to 16,384, but BPE stops when no useful
  merges are left (about 13.7k on this corpus). Byte-level BPE never needs `<UNK>`.
  The older 4,096 tokenizer is kept as `tokenizer/bpe/tokenizer_4096.json`.
* **4 heads** instead of 1: same parameter count, and each head can learn a
  different pattern.
* **Context 128** instead of 64: many answers are longer than 64 BPE tokens.
* The old word-level checkpoints cannot be loaded: token ids are different.

## UI

Colourful (cyan, indigo, rose) responsive chat for desktop and phone. While ELVARN answers, a live card shows the real steps and measurements from the backend (prompt tokens, tokens generated, speed, confidence). It does not search or research anything. Each new question scrolls to the top, and the send button becomes a stop button during generation. Voice input (🎤) and read-aloud
(🔊) use the browser's built-in speech features: use Chrome or Edge on
`localhost`. Voice input may send audio to the browser vendor's speech
service. Settings (temperature, max tokens, top-k, greedy, voice, speed,
listening language) are in the ⚙️ panel.

## Web search with your own SearXNG (optional)

The "Web search" switch in the settings panel asks a SearXNG server you run yourself for fresh results, shows them as citations and gives the model a few short snippets as notes. No API key and no paid search service. Without SearXNG the chat works as before and says the answer was not checked against live web results.

```powershell
# 1. In .env (copy from .env.example) set a secret and a pinned image version:
#      SEARXNG_SECRET=<output of: openssl rand -hex 32>
#      SEARXNG_IMAGE_TAG=<a dated tag from https://hub.docker.com/r/searxng/searxng/tags, never "latest">
# 2. Start SearXNG (listens on 127.0.0.1:8080 only, so nobody else can reach it)
docker compose -f docker-compose.searxng.yml --env-file .env up -d
# 3. Start ELVARN as usual. It looks for SearXNG at SEARXNG_BASE_URL (default http://127.0.0.1:8080)
# Stop it with: docker compose -f docker-compose.searxng.yml down
```

Settings: `SEARXNG_BASE_URL`, `SEARXNG_TIMEOUT_SECONDS`, `SEARCH_RESULT_LIMIT`, `MAX_SNIPPET_LENGTH` (see `.env.example`). SearXNG config: `infra/searxng/settings.yml`. Only titles, links and snippets are used; pages are never opened. Results depend on the search engines SearXNG asks, which may rate-limit it.

## File upload and format conversion

Use the paperclip button (or drag a file onto the chat), then type something like "convert this to pdf" or press a "Convert to" button. You get a download card. The conversion is done by plain server code in `backend/files/`, **not by the language model**: the 17M model never reads or rewrites your file, and the reply ("Converted notes.txt to PDF (12 KB).") is a fixed template. Asking to summarise, translate or rewrite gets an honest "I only change formats" answer. Any other message goes through the normal chat unchanged.

| From (upload) | To |
|---|---|
| txt | md, html, csv (one row per line), json, docx, pdf |
| md | txt, html, json, docx, pdf |
| csv | txt, md, html, json (list of objects), docx, pdf |
| json | txt, md, html, csv (only a list of records or rows), docx, pdf |
| html | txt, md, json, csv (first table only), docx, pdf |
| docx | txt, md, html, json, csv (first table only), pdf |

What is kept: text, headings, bullet items, code blocks and tables. **Not kept:** layout, fonts, colours, images, page structure. PDF is output only (reading PDFs safely needs a heavy library). The PDF writer uses built-in fonts, so only English / Western European characters are drawn; other scripts become `?` and the reply says how many. "Any file type" is not supported on purpose: each type needs its own safe reader, and programs, archives, macro files (`.exe .js .zip .docm .xlsm .svg` ...) are always refused.

Endpoints: `POST /api/files` (the raw file as the body, name in the `X-File-Name` header, percent-encoded) returns `{file_id, name, size, detected_type, supported_targets}`; `POST /api/files/{id}/convert` with `{"target": "pdf"}` returns `{download_id, name, size, format}`; `GET /api/files/{download_id}/download` returns the file as an attachment; `DELETE /api/files/{id}` removes an upload. `/api/chat` and `/api/chat/stream` accept an optional `file_ids` list; a conversion turn returns `files` and `file_action` (streaming adds a `file` event before `done`).

Viewing and copying: click a file card in the chat (or the file chip inside the input box) to open a right-side panel that shows the file's text, with Copy, Download and Close buttons (Esc also closes it). The "+" button at the left of the input box attaches a file; the chip, its remove button and the small "Convert to" buttons sit inside the input box. The panel is fed by `GET /api/files/{id}/preview` (works for upload ids and download ids) which returns `{name, format, size, text, truncated, preview_note, kind, label}`: text only, at most 200,000 characters (`truncated` is set when longer), `Cache-Control: no-store`, same expiry, 404 and per-visitor rate limit as downloads, and nothing is logged. TXT/MD/HTML/CSV/JSON files are returned as their own text (HTML is shown as source, never rendered); for DOCX and PDF the preview is the extracted text only (the PDF itself is never parsed). The browser shows it with `textContent`, never as HTML.

Limits and storage (env vars in `.env.example`): 5 MB per upload (`ELVARN_MAX_UPLOAD_MB`), 20 MB in the store (`ELVARN_MAX_STORE_MB`), 20 files per visitor (`ELVARN_MAX_FILES_PER_VISITOR`), files deleted after 1 hour (`ELVARN_FILE_TTL_SECONDS`), folder `ELVARN_FILE_STORE` (default `backend/file_store/`, git-ignored, emptied at start-up). Files are temporary: nothing is kept long term. In public mode uploads, conversions and downloads share the per-visitor rate limit.

Security: size is limited while reading; type is decided by extension AND content (they must agree); names are cleaned and never used as paths (files are stored under random names with random 192-bit ids); docx zip bombs, macros and XML entities are refused (any DTD/entity makes the file be rejected, so no XML expansion attack is possible); HTML input is reduced to plain text (scripts, styles, frames, forms and every attribute are dropped) and HTML output is escaped, carries a strict CSP, and is only ever sent as an attachment; CSV cells starting with `= + - @` get a leading `'`; downloads send `nosniff`, `no-store`, a fixed content type and a sandbox CSP; conversions run in a worker thread with a timeout and size caps; logs hold only type, size and timing. The UI was not tested in a real browser by the automated tests.

## Answering from web notes (512 context + RAG fine-tune) - done once, commands to repeat it

Goal: make the model good at answering FROM the "Web notes" that live web search puts in the prompt. This was run once
(results in "Where things stand" below). Steps (every step writes to a NEW folder and never overwrites):

```powershell
# 1. Longer context: 128 -> 512 (copies every weight; short inputs give exactly the same logits)
.venv/Scripts/python.exe backend/training/extend_context.py --init-from <final checkpoint>.pt --out-dir backend/training/checkpoints_bpe/ext512 --sequence-length 512

# 2. Training data in the live prompt format (already built once into backend/data/rag_v1; to rebuild use a new --out-dir)
.venv/Scripts/python.exe backend/data_tools/build_rag_dataset.py --out-dir backend/data/rag_v2 --seed 1

# 3. Fine-tune (slow on CPU: roughly 1 hour per epoch, estimate)
.venv/Scripts/python.exe backend/training/continue_train.py --init-from backend/training/checkpoints_bpe/ext512/extended.pt --data-dir backend/data/rag_v1 --out-dir backend/training/checkpoints_bpe/rag_ft --epochs 3 --batch-size 8 --optimizer fresh --learning-rate 5e-5 --warmup-steps 50 --patience 2 --seed 42 --threads 8

# 4. Evaluate before and after on the fixed hold-out (backend/eval/rag_eval.json; results go to backend/eval/results/)
.venv/Scripts/python.exe backend/eval/run_rag_eval.py backend/training/checkpoints_bpe/ext512 backend/training/checkpoints_bpe/rag_ft
```

Compare the two rows: key-fact coverage and correct refusals should go up; invented numbers/names and repetition should go down.
At answer time the server turns on `repetition_penalty` (1.15) and `no_repeat_ngram_size` (4) only when web evidence is in the prompt;
clients can set both in the request (`repetition_penalty` 1.0-2.0, `no_repeat_ngram_size` 0-10; 1.0 / 0 = off).

## Where things stand (13 Oct 2026)

**Deployed on Render (free plan):**

| Service | What it is | Address |
|---|---|---|
| `elvarn` | the chat site + model, auto-deploys from `main` | https://elvarn.onrender.com |
| `elvarn-search` | protected SearXNG (`search_service/`), Docker, only answers requests that carry a secret token | https://elvarn-search.onrender.com |

**The live model** is `deploy/models/17m_rag`: 17,152,000 parameters, 512-token context, vocabulary 16,384 (tokenizer trained on the v2 data).
Stage 1 trained 5 epochs on Wikipedia / Dolly / OASST / the original domain text (validation loss 3.604). Stage 2 fine-tuned 3 epochs on
"notes, question, answer written from the notes" examples (RAG validation loss 2.408). The older models (6.7M and 0.8M) were removed from
`deploy/models` on 13 Oct 2026; they are still in git history (for example `git checkout 8471762 -- deploy/models/7m_epoch2`).
**Rollback** means restoring a model folder from git history, then setting `ELVARN_CHECKPOINT_DIR` on Render to that folder and redeploying.

**Measured quality (be realistic, it is a small model):**
- Writing score on the 82 original validation documents, bits per character (lower is better): old live model 1.139, 17M before RAG 0.953, live model 1.120.
- 60-case RAG test (`backend/eval/run_rag_eval.py`, results in `backend/eval/results/`): facts copied from the notes 5.6% -> 22%, cites a real note
  about 70% of the time, still invents details in about 45% of answers and sometimes refuses wrongly. Answers can be wrong; the sources shown under them are the reliable part.
- Memory on Render: about 361 MB steady (limit 512 MB). Generation uses a KV cache (same text as without it, much faster).

**Live web search:** in India Law mode every question is searched (with legal context added to the query); other modes search fact questions.
Results must contain the question's distinctive words and numbers, adult results are dropped and every search uses strict safe-search.
The free search engines are unreliable from a cloud address, so some questions return no sources (the page then says the answer was not checked against the web).
Environment variables on the `elvarn` service: `SEARXNG_BASE_URL`, `SEARXNG_AUTH_TOKEN` (the same value as `SEARCH_PROXY_TOKEN` on `elvarn-search`),
`SEARXNG_TIMEOUT_SECONDS`, `ELVARN_MAX_UPLOAD_MB`, `ELVARN_MAX_STORE_MB`. Secrets live only in Render's environment and the local `.env` (git ignores it).

**Not in git on purpose:** raw and processed data, the RAG dataset (`backend/data/rag_v1`), training checkpoints and logs. See `DATA_SOURCES.md` for the data and its licences.

**Ideas for the next step:** longer, human-written RAG answers; copy-biased decoding (make words from the notes more likely); a better search source for Render.

## Deploying on Render

The repo is ready for a Render **Blueprint** (`render.yaml`).

1. Push this repo to GitHub (the weights-only models in `deploy/models/` are committed on purpose).
2. On <https://dashboard.render.com> choose **New > Blueprint**, connect the GitHub repo, and press **Apply**.
3. Render runs `pip install -r requirements-render.txt` (CPU-only PyTorch) and then
   `python -m uvicorn backend.api.server:app --host 0.0.0.0 --port $PORT`.
4. When the deploy is live, open the `https://<your-service>.onrender.com` address. The page and the API
   are served by the same server, so no other setting is needed.

Settings (environment variables, already set in `render.yaml`):

| Variable | Meaning |
|---|---|
| `ELVARN_CHECKPOINT_DIR` | Model folder: `deploy/models/17m_rag` (17.15M parameters, 512 context, RAG validation loss 2.408, the default). |
| `ELVARN_PUBLIC` | `1` = public site: per-visitor rate limit, cap on simultaneous replies, `/api/reload` disabled. |
| `ELVARN_RATE_LIMIT` | Chat requests per visitor per minute (default 20 when public). |
| `ELVARN_MAX_CONCURRENT` | Replies generated at the same time (default 2 when public). |

Notes:

* **Memory.** Render's free plan has 512 MB of RAM, which is tight for PyTorch. If the service restarts with
  "out of memory", use a plan with more RAM (the 17M model uses about 361 MB on Render, measured).
* **Free plan sleeps** after about 15 minutes without visitors and takes about a minute to wake.
* The site has no login. Anyone with the link can use it, which is why the rate limit exists.
* ELVARN is a small model. Its replies can be wrong, and the page says so. Do not present it as a source of legal facts.
* To deploy a newly trained model: `python backend/training/export_deploy.py <checkpoint_dir> deploy/models/<name>`,
  commit the new folder, point `ELVARN_CHECKPOINT_DIR` at it and push.
